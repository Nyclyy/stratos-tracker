# Stratos

A lightweight flight-simulation companion: live map, public ADS-B traffic, airports and charts, a career logbook, flight replay, landing analytics, route planning, weather briefings, and a secure phone dashboard.

Stratos runs as a static website/PWA, an Electron desktop app, and an optional local Python simulator bridge. It is designed to be useful without a simulator, and explicit about what is live, estimated, or unavailable.

## What is implemented

| Area | Status |
| --- | --- |
| Map, airports, navaids, public ADS-B traffic, METAR/TAF | Working; data-provider dependent |
| Integrated charts (ILS/LOC free, the rest Premium) | The current FAA d-TPP catalogue per airport (diagrams, SIDs, STARs, approaches, minimums, hot spots) in a source-agnostic provider registry, a bundled pdf.js viewer with zoom, pan, fit, reset, pages, previous/next document, full screen and a document cache, and a trusted Premium gate. **ILS and LOC approach charts open for everyone**; the other categories need a verified licence. Search accepts an ICAO code or an airport name, every row is labelled Free or Premium, the airport header names the airport, country and available categories, and the last airport/chart is restored on return. Coverage is the United States and its territories; Canada, Europe and Australia show publisher links only (no embedded or mirrored charts), and **Open PDF…** displays a chart you downloaded from that publisher locally, without uploading or caching it |
| Route vertical profile | Planned altitude, climb/cruise/descent, TOC/TOD and per-waypoint inspection from the same estimate the planner reports; imported flight-plan altitudes are kept as constraints. TOC/TOD are interpolated **inside the route leg they belong to** by a pure profile module: the plan's own altitudes end the climb and start the descent, a measured (or default) gradient fills the gaps, and a gradient-derived marker is marked `≈` so an estimate never reads as a planned figure |
| Route weather along the plan | NOAA METAR at up to eight airports on the route with surface wind components against the flown course and honest IFR/gust/crosswind notes; real-world only, not winds aloft or simulator weather |
| Offline vector world map | Working; the **World** style draws bundled Natural Earth country outlines with muted country names, letter-spaced continent names and italic ocean names, adds seas only when zoomed past a whole-world view, and needs no tiles, key or network |
| X-Plane UDP bridge, MSFS SimConnect (optional package) | Implemented; not tested against a live simulator here |
| Flight recording, crash recovery, duplicate prevention | Working, tested |
| Flight replay with recorded/interpolated distinction | Working for flights with a recorded track |
| Landing analytics with per-aircraft thresholds | Working; runway/touchdown values are estimates |
| Career dashboard, records, milestones, drill-down | Working, with customizable tiles |
| Interactive route planner | The planned route is drawn on the Flight Deck map itself as soon as it exists — fitted to the route, labelled, with a **Route** layer toggle and two-way sync with the planner. The planner page keeps its own editing map with a collapsible plan sidebar and route header; selectable legs and waypoints; add, delete, reorder and drag waypoints; undo; a leg inspector with geodesic distance, initial true course, magnetic course only when variation is supplied, ETE at the planned/live groundspeed, leg position and endpoint coordinates; total distance/legs/ETE and live remaining distance. PLN/FMS/GPX import/export and SimBrief import stay on the same route |
| Aircraft checklists | Ten ToLiss/FlightFactor profiles plus a generic checklist, including a dedicated A340-600 flow; aircraft detection from telemetry with manual override; phase inference from groundspeed/altitude/vertical speed; per-flight progress, compact/full modes, custom items, import/export and reset; optional phase callouts off by default; **community simulator aid, not a verified aircraft manual** |
| Phone pairing on the local network | **One tap, no QR and no URL.** The bridge answers multicast DNS for `stratos.local`, so the phone opens `http://stratos.local:8765/pair/connect`, enrolls itself and lands on the live dashboard; telemetry then reconnects on its own after a Wi-Fi change or bridge restart — the map also treats twelve seconds of silence as a dead socket and reopens the stream, because a restarted bridge does not always close the old one. The QR/six-digit code remains as a fallback for networks that block multicast. Every phone gets its own HttpOnly secret, remembered across visits; the PC lists paired phones and can forget one or all; revoked streams close within ~5 s |
| Flight Deck shell | One grouped rail (Flight Operations / Flight Intelligence / Application) that opens icon-only, expands to a labelled sidebar, names each icon on hover and keyboard focus, and shares one keyboard ring with the bar; a top bar with the wordmark and its live state line, one centred search, Support Us / Go Premium and the UTC clock, and a full-bleed map: the flight card floats over it with real telemetry and a corner badge names the place and the live aircraft count |
| Flight overview dashboard | Reports the simulator link, the live flight, the saved route pair, planned cruise level, distance, ETE and airborne progress, and admits a value it does not have instead of inventing one |
| Top of descent from your own descents | Working; the bridge measures the real gradient of each completed flight and the profile uses it, falling back to 200 ft/nm until one exists |
| Route symbols, labels and selection | One chart symbol per meaning (en-route fix, airway fix, SID, STAR, airport, VOR, NDB, unclassified navaid, TOC/TOD), long legs carry their distance and heading, labels give way instead of overprinting, and a click or tap selects a point with a purple halo and thicker glyph. Selection is a drawing layer only: the waypoint-to-waypoint line is byte-for-byte unchanged. A plan imported in the Route Planner keeps its SID/STAR tags, its airways and its stored SimBrief plan, so the same symbols and the same procedures appear on the map and in the tracking card |
| Terminal procedure geometry | SID and STAR runway transitions follow real published legs, from the runway threshold to the procedure's terminal fix, in either of two providers. The bridge reads X-Plane 12's CIFP folder and resolves each fix against the simulator's own fix, navaid, airport and runway records. When the simulator has no data for the airport — MSFS, or no X-Plane installed — the dataset Stratos ships (`navdata/cifp`, the FAA's public-domain CIFP, US airports, rebuilt by `scripts/build-navdata.py`) supplies the same geometry. Only the plan's own SID/STAR and runway are used (including a combined "both runways" transition, labelled as such), and only the legs the plan does not already draw are painted, under the unchanged waypoint line. Procedures the source publishes without any runway leg — most FAA STARs, which carry a common trunk plus en-route transitions — are drawn from their verified trunk instead of being dropped, and the runway is never joined to them by a straight line. A leg the data cannot place is counted and reported, never guessed; without that data no path is drawn and the card says why. The AIRAC cycle and provider are shown |
| Flight trail and aircraft card | The bridge records the flight from its first movement; the map and the phone draw that recorded path rather than starting at the moment the page opened, and a new flight never joins the previous one. Selecting **any** aircraft — your own or a VATSIM/ADS-B target you click — draws that aircraft's own recorded path, not only yours. Positions are recorded for every aircraft in view on each traffic refresh and kept per aircraft id; the page batches them to the bridge, which keeps them for 45 minutes in `traffic_trails.json`, so the path survives a page reload, a bridge restart and a browser refresh, and is served back to anything the bridge hosts. A trail is always what Stratos actually observed — no history is invented. On both maps — the Flight Deck and the phone's small live map — the path is one continuous line coloured by **height above ground** from one shared ramp: white while taxiing and on the runway, then blue through green and yellow to orange and magenta at the flight levels, so the climb and the descent are readable at a glance. The recording carries AGL per sample; a track without it is coloured by height above its lowest point, and a route preview with no altitudes keeps the plain accent line. Traffic feeds publish only a current position, so a target's trail starts when Stratos first sees it and the card says how much has been recorded. The phone's own live map draws that nearby traffic too — the VATSIM pilots it can read itself plus the aircraft the bridge has already polled — with a **Traffic** layer button; tapping a target selects it, reports only the fields it actually has (type, filed route, altitude, speed, heading, distance) and draws that aircraft's path from the same bridge store, so the trail on the phone matches the one on the PC and survives a reload. A phone paired through the relay instead (on a different network) is served by the relay: the bridge posts the same traffic list and the new trail samples to `POST /api/traffic` every 15 s, and the phone reads them with its read token, so the hosted page shows the desktop's traffic and the same recorded paths rather than a blank map. The aircraft card expands to photo, registration, type, phase, planned cruise and runways, and minimizes to a live strip plus SID/STAR with the departure runway under the SID and the arrival runway under the STAR |

| Updates and release notes (Windows, web and PWA) | Every release publishes a categorised changelog and update manifest, generated from the tagged commits and able to be written by hand per version in `release-notes/curated.json`. A packaged build checks the newest stable GitHub release in the background, verifies the download against the published SHA-512 and installs it on quit. A download left over from an earlier session is applied at the next launch, without a prompt. **Settings → Updates** shows the installed and latest versions, the last check, progress, errors and a retry, every previous release with its notes, and a **Restart to update** action; a newer build opens a modal with **Update now**, **Remind me later** and **View full changelog**. ## Quick start

- Website: open `index.html`, then `app/`.
- Local development: `npm run dev` serves `app/` on http://127.0.0.1:8123 and proxies live ADS-B traffic, which browsers cannot fetch directly (the mirrors send no CORS headers). A plain static server can still serve the files, but live ADS-B then reports why it is unavailable.
- Windows: download `Stratos-Setup.exe` from the latest GitHub release, or build with `npm ci && npm run dist:win`.
- Simulator bridge: `python3 stratos_bridge.py` (the desktop app starts it automatically).
- Tests: `npm test`, `npm run test:py`, `npm run test:integration`.

No API keys are required for the app. The optional relay is a small Node server in `relay/`; see the deployment guide.

Running from source (`npm start`) reports a labelled development entitlement, so the Premium surfaces can be tested without a licence service. A packaged build needs `STRATOS_DEV_PREMIUM=1` or a configured `STRATOS_ENTITLEMENT_URL`.

## Honest limitations

SID and STAR paths are drawn from the fixes the imported plan lists, plus the procedure geometry the bridge can read: X-Plane 12's own CIFP on that PC, or — when the simulator has none for the airport, as with MSFS, whose navdata is proprietary and unread — the FAA dataset Stratos ships in `navdata/cifp` for United States airports. Most ARINC 424 files publish no runway leg at all, only a common trunk plus en-route transitions; those verified legs are drawn, the runway is not joined to them by an invented line, and the tracking card says so. Where neither provider has the procedure, nothing is drawn, the plan's own fixes still appear as the plan lists them, and the card says which plan a SID and STAR came from and why a path is missing.

The route planner, checklist engine, one-tap LAN pairing (mDNS name, auto-enrollment and reconnect) and the MSFS connector were exercised on Windows 11 with Chromium and the real Python bridge. X-Plane telemetry (including the UDP dataref identity read) and a real iPhone/Safari session or production relay host were not available, so those paths are implemented and source-tested but still need a flight on your hardware. Checklist content is community-compiled from public procedures and is deliberately labelled unverified; it does not replace the aircraft add-on's own checklists or manual. The bridge listens on the LAN by default for pairing, protected by the access token and per-phone cookies — use it only on a trusted network and never forward port 8765 from a router. The old `env.download` Vercel token is removed from the tree but remains in Git history — revoke it in Vercel.
