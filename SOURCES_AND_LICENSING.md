## Aircraft photos

- **Registration lookup** — a registration the feed did not carry is worked out when an aircraft is opened on the map: from the simulator's aircraft title or livery for your own airframe, from the Mode S address in [hexdb.io](https://hexdb.io) for live traffic, or, when VATSIM is the only source, from a live callsign search (`api.adsb.lol/v2/callsign/<callsign>`, through the app's `/api/traffic` route where the deployment has one). One lookup per aircraft per session. A registration found this way is shown as detected, never as feed data, so a photo of a different airframe is not presented as yours.
- **Planespotters.net photo API** — `api.planespotters.net/pub/photos/reg/<registration>`. A photo is requested only when an aircraft is opened on the map, at most once per registration per session, through the app's own `/api/photo` route (the hosted deployment, the local dev server, or the Python bridge's `/api/photo`, which caches a found photo for a day and a miss for an hour), which also carries the application User-Agent the API requires. Only the first published photo is shown, with the photographer's name and a link to its Planespotters page, as their terms ask. Images are loaded from `t.plnspttrs.net` and are not copied into Stratos or redistributed with it. A registration with no published photo says so; no other aircraft's photo is substituted.

## Airport and navigation data

- **OurAirports** — public domain (CC0). CSV data is downloaded at runtime from `ourairports.com` / the maintained GitHub mirror and cached. Attribution is included in the UI even though CC0 does not require it.
- **OpenStreetMap** — Open Database License (ODbL). Airport layout/taxiway geometry is queried from the Overpass API (or the bridge cache). Main map tiles come from OpenStreetMap and Esri World Imagery (the World and Basic styles request no tiles at all); the Light, Dark, replay and route-preview surfaces use Esri's World Light/Dark Gray canvas, which needs no key or account. Attribution is shown on both map surfaces: “© OpenStreetMap contributors · Esri imagery” and “© Esri, HERE, Garmin · © OpenStreetMap contributors”. See https://openstreetmap.org/copyright and the respective provider terms.
- **Terminal procedures** — two providers. (1) The simulator's own data on the pilot's PC: X-Plane 12's CIFP folder (`Custom Data/CIFP` when present, otherwise `Resources/default data/CIFP`), with fixes, navaids, airport points and runway thresholds from that installation's `earth_fix.dat`, `earth_nav.dat`, `earth_aptmeta.dat` and the CIFP `RWY:` records. That data is licensed to the pilot by Laminar Research/Navigraph and is **not** copied into, bundled with or redistributed by Stratos. (2) The dataset Stratos ships in `navdata/cifp`: the FAA's **Coded Instrument Flight Procedures** (`FAACIFP18`, ARINC 424), a work of the US Government in the public domain, converted to one JSON file per airport by `scripts/build-navdata.py`, with runway threshold coordinates from OurAirports (CC0). It carries the published SID and STAR legs from each runway transition to the procedure's terminal fix for United States airports; it is used when the simulator has no data for the airport, which is what gives MSFS users real procedure geometry (MSFS navdata itself is proprietary and is not read). The AIRAC cycle and effective date travel with the dataset in `navdata/cifp/index.json` and are shown in the app. A leg whose fix the source cannot place is reported as skipped, never guessed. No procedure is downloaded at runtime.

## World map layer

- **Natural Earth** — public domain (no restrictions, no attribution required; credited anyway). The bundled file `app/js/data/world.js` is generated from the 1:110m `admin_0_countries`, `geography_regions_polys` and `geography_marine_polys` vectors by `scripts/build-world.mjs`, which rounds coordinates to two decimals and simplifies them. It contains country outlines and label points, continent label points and ocean/sea label points. No political boundary claim is intended: the outlines are the Natural Earth dataset as published, and borders are drawn as thin lines rather than as colours. The tracker reads it as a world layer; **globe mode on both maps** — the Flight Deck tracker's and the Flight Planner's — reads the same file for its coastlines in its default **Outlines** surface, and each page loads it only when a globe is first switched on, so no other page pays for it. Outlines is what a globe draws unless the pilot chooses otherwise: no request is made and no decoder is built until a surface that needs tiles is selected.
- The World style draws only this file. It makes no network request, so it works offline and needs no key. Rerun the build script with `--download` to regenerate it.

## Globe imagery and terrain elevation

A globe — the Flight Planner's and the Flight Deck tracker's, which share one engine, `app/js/lib/globeview.js`, over the same imaging module — can be painted from two public services, and only when the pilot asks for one of them. Tiles are read straight from the publisher with the browser's own CORS-enabled request: no key, no proxy, no copy in the repository, nothing redistributed, and the publisher is named both on the sphere and permanently in the map readout. `app/js/lib/earthview.js` is the whole integration; the levels, the attribution, the licensing text and the limits live there beside the code that uses them. Each map remembers the projection and surface the pilot last chose, and on the tracker a georeferenced approach chart is a flat sheet: opening one leaves the globe for the chart and closing it returns to the globe with the route reframed, which the map says when the globe is asked for during a chart.

- **NASA GIBS — Blue Marble Next Generation** (the globe's **Imagery** surface). A cloud-free global mosaic from NASA's EOSDIS, served as WMTS tiles from `gibs.earthdata.nasa.gov` in the 4326 "best" pyramid (512-pixel tiles whose matrix is not a power of two, which is why the level widths are read from the service's own capabilities rather than assumed). NASA content is generally not subject to U.S. copyright and the service is published for reuse in applications, so no key or licence purchase is involved; NASA's identifiers and logos are not used, and nothing implies NASA endorsement of Stratos. NASA asks for this acknowledgement, which Stratos shows in the chart readout while the surface is in use: *“We acknowledge the use of imagery provided by services from NASA's Global Imagery Browse Services (GIBS), part of NASA's Earth Science Data and Information System (ESDIS).”* Blue Marble imagery is additionally credited to **NASA Earth Observatory**. Levels 1-5 of the pyramid are used, chosen so the source is about twice as fine as the sphere on screen; a globe a few hundred pixels across therefore reads a handful of tiles, never a worldwide pyramid. NASA's published bulk-download process (more than 1,000,000 tiles in 24 hours) does not apply to this use, and tiles are never mirrored or re-served.
- **AWS Open Data Terrain Tiles — Mapzen** (the globe's **Relief** and **Elevation** surfaces, and every terrain elevation reading). Published by Mapzen, a Linux Foundation project, hosted by AWS in `s3://elevation-tiles-prod` and served as terrarium-encoded PNGs (`https://s3.amazonaws.com/elevation-tiles-prod/terrarium/{z}/{x}/{y}.png`), height in metres = `(R * 256 + G + B / 256) - 32768`. It is a composite, not one DEM: **USGS 3DEP** and **GMTED2010** (public domain, USGS credit requested), **NASA SRTM** (public domain, with a copyright assertion attached to some products distributed outside the United States), **NOAA ETOPO1** (public domain in the U.S., formal NOAA/NCEI credit), and regional datasets — ArcticDEM, EU-DEM, Canada's CDEM and national elevation models — whose terms vary by source and by region. The bucket answers CORS for browser readback, which is what makes shading and elevation sampling possible at all rather than only blitting a picture. Stratos credits the dataset on the sphere and in the readout as *“Terrain elevation: AWS Open Data Terrain Tiles (Mapzen), from USGS 3DEP and GMTED2010, NASA SRTM and NOAA ETOPO1”*, and carries the source-terms note with it.
- **Two levels, for two different questions.** The surface is *drawn* from a level chosen so a tile is about twice as fine as a pixel of the sphere (level 2-6 by sphere size: about thirteen tiles for a whole visible face), because shading a hemisphere from the globe's own drawing level is enough detail for what the sphere can show. An *elevation reading* is taken from a deeper level — level 9, about 230 m per pixel at mid-latitude — and a radius scan from a level near its own sample spacing, which keeps a 20 NM scan and a 320 NM scan to about fourteen tiles each. Elevation is never read from the coarse drawing level, which would report a mountain range's average as a point's height. Levels are stated in the readout rather than implied.
- **Terrain elevation is a display product, not a navigation one.** ETOPO1 states that it is not suitable for navigation; the assembled tiles are a situational-awareness picture for a simulator map. The readout says so on every terrain reading, reports how many of its samples actually had data, and states the level and ground resolution they came from. No terrain elevation is used for terrain clearance, minima or any operational purpose, and the surface is never presented as an obstacle or terrain-awareness function.
- **What is not integrated.** No provider's imagery is bundled, mirrored or proxied, no Google/Esri/Bing imagery is read for the globe, and no commercial terrain or obstacle database is present. A surface the pilot does not choose costs nothing: the Outlines default makes no request, and a failed or offline request falls back to the bundled outlines with the failure reported in the readout rather than a substitute pattern being drawn.

## Route Discovery

- Route recommendations are computed locally from the same airport records above: identifiers, coordinates, elevation and published runway lengths. Distances are great-circle distances; durations are estimates at a fixed cruise speed plus ground time, never ATC routings or winds.
- **Navigation points around the chart.** The Flight Planner's query (20/40/80/160/320 NM, 40 NM by default, with the radius circle drawn only if the pilot turns it on) answers from two sets, and never from a guess. Airports and radio navaids come from OurAirports (CC0) — the bridge's worldwide list where it is connected, the bundled snapshot otherwise. En-route fixes and the simulator's own navaids come only from the simulator's navigation data (`/navdata/near`, read in place from the X-Plane CIFP installation as described above; that data is licensed to the pilot and is never copied into Stratos). Where the bridge is not available, no fixes are shown and the readout says why. Every record is measured with a haversine radius, so the query circle is a real distance on the ground at every latitude, and a chart tap is resolved to a published identifier or to a clearly-labelled custom coordinate — never to a generated name.
- **Terrain elevation comes from the terrain tiles above, and only from them.** The chart shows four altitudes, each with its own source and its own label: aircraft altitude from the simulator over the live bridge, airport elevation from the airport record, a navigation point's published elevation where a dataset supplies one, and — on the globe, once the pilot has read terrain — the ground elevation at the centre and the highest of a stated number of samples inside the query radius. Between those, ground elevation is not available anywhere in Stratos, and the chart readout and the performance panel say so rather than showing a number they do not have; the terrain rows also state the level and the ground resolution they were read at.
- Terrain mentions come from a coarse set of geographic boxes (Alps, Rockies, Andes, Himalaya, Scandinavia, Iceland, Caribbean, Mediterranean, Japan, Hawaii, New Zealand, Patagonia, Southeast Asia, North Africa, Australia) sampled along the great circle. They describe terrain the path plausibly overflies, not a verified overflight of a specific landmark. No landmark, procedure, airway or navaid is invented.
- Storm Chasing is a **simulated** scenario. No live storm data is fetched or implied, and nothing on the page is real-world weather advice.
- Night Flight notes that lighting and city scenery depend on the user's simulator; no scenery database is queried.
- Preview map tiles are the same Esri gray-canvas tiles used by replay, with attribution shown in the corner of the map.

## Aircraft checklists

- Checklist content is a **simulator aid**, compiled from publicly documented Airbus/Boeing normal-flow structure and the publicly described ToLiss/FlightFactor add-on feature sets. No manufacturer manual, proprietary checklist card, or add-on EFB checklist file is copied, bundled or redistributed.
- Every profile is marked `community` and carries the same disclaimer in the UI: it is not verified against the aircraft manufacturer or the add-on manual and is not for real-world flight. The A340-600 profile describes the four-engine layout, fuel/trim-tank planning and long-haul considerations; it does not instruct the pilot to clear a normal ECAM memo such as `T TK XFRD`.
- Where the ToLiss EFB already provides a checklist, Stratos presents its own companion list and does not try to control or replace the aircraft's systems. No checklist item operates a switch automatically; the optional callouts are speech only and are off by default.
- Users can add, edit, import, export and reset their own checklist. A custom list is stored locally and remains labelled as unverified.

## Weather

- **NOAA Aviation Weather Center** — U.S. Government work, public domain. METAR/TAF are fetched from `https://aviationweather.gov/api/data/` either through `/api/weather` (Vercel) or the bridge’s `/weather`. Source and observation time are shown. NOAA availability is not guaranteed.
- **Route weather** reuses those same METARs for the airports on a planned route, at most eight stations per route. It reports the surface wind component against the course the route actually flies, and derives flight category only from reported visibility and ceiling. It does not claim winds aloft, turbulence, radar or simulator weather, and a station without a report is shown as unknown rather than estimated. This is real-world weather, kept visually separate from the simulator's own conditions.
- **Weather imagery over the chart is not integrated.** The Flight Plan app's chart draws the base map, the route and the navigation data, and nothing is layered over it as if it were observed weather — no simulated radar, no interpolated cloud. Adding a real overlay needs a provider that (a) serves georeferenced, time-stamped imagery in a tile or image pyramid form, (b) grants third-party display inside another application in writing, and (c) states an update interval and a refresh policy the client may follow. A national weather service's public data is not by itself such a grant, and a licence key would be held server-side, in the bridge or the deployment's own function, never in the page. Until a provider with those terms is selected and its key is configured, the chart has no weather layer to toggle, which is why the Flight Plan app offers none.

## Traffic

- **adsb.fi**, **airplanes.live**, **adsb.lol**, **OpenSky Network** — community/public ADS-B sources with their own terms and rate limits. Aircraft shown are real reports from these providers. Stratos does not claim complete or worldwide coverage, and none of this is for real-world navigation.

## Charts

- **FAA Digital Terminal Procedures (d-TPP)** — U.S. Government work, public domain. Stratos reads the FAA's own `d-TPP_Metafile.xml` for the current 28-day cycle, so the catalogue carries the publisher's chart codes, titles, document names, amendment dates and the publication window. Documents are fetched on demand from `aeronav.faa.gov` (directly through the local bridge, or through Stratos' own narrow pass-through on the hosted site) and rendered in the app by the bundled pdf.js build. Stratos does not bundle, mirror or sell a chart library; the FAA PDFs stay on the FAA's servers and are cached on the user's own device only so the same chart is not downloaded twice.
- **Coverage** is exactly what the FAA publishes: airports in the United States and its territories. There is no invented coverage anywhere else; an airport without FAA charts gets an explicit "not covered / no charts" state instead of a generated diagram. Canada, Europe and Australia get links to the publisher that owns their charts, and the viewer can open a PDF the pilot downloaded from it.
- **Provider registry.** `app/js/lib/chartproviders.js` declares each provider's regions, categories, document format, update method, attribution and licence position. Only `faa-dtpp` has `status: 'integrated'`; the others are `link-only` (or EUROCONTROL's `portal` entries). The Charts page asks the registry before it fetches anything, so it cannot advertise a category for a region whose charts Stratos may not display.
- **Charts outside the United States are never mirrored.** NAV CANADA owns the Canada Air Pilot and its IFR charts and licenses them commercially. In Europe, DFS, LVNL, Avinor, Austro Control and PANSA require written permission to reproduce their AIS charts, and for the other states reviewed no third-party reuse grant was found. EUROCONTROL EAD Basic is free after registration but is a consultation tool, not an app feed. Airservices Australia publishes the Australian AIP and terminal procedures; no redistribution grant was found. The Charts page therefore links to the publisher (and the EUROCONTROL AIS index) instead of copying, framing or proxying anything.
- **Your own files.** A chart downloaded from one of those publishers can be opened with “Open PDF…”. The file is read from disk, rendered locally, never uploaded and never cached as an official document, and the viewer labels it as not coming from a verified source.
- **Which charts are free** is a product rule, not a licence term: these documents are public domain either way. ILS and LOC approach charts (including ILS OR LOC, LOC/DME and localizer-only procedures) open for everyone; diagrams, SIDs, STARs, RNAV/RNP, VOR, NDB and every other category are gated behind Stratos' own Premium entitlement. There is no daily quota on the free charts.
- **ChartFox** is not used at all: no redirect, no frame, no scraping. The old Flight Deck launcher pointed at `chartfox.org`; that path is gone.
- **NAV CANADA** publishes Canadian charts commercially (`NAV CANADA Aeronautical Publications`). Their terms do not grant redistribution or API display rights to a third-party app, so no Canadian charts are imported. A NAV CANADA adapter should only be added under a written licence; the catalogue and viewer are source-agnostic, and the provider registry has the entry ready to switch to `integrated` once a licence exists.
- **Airservices Australia** publishes the Australian AIP and terminal procedures. No redistribution grant was found, so Australian airports list the Airservices portal and use the same local-file path.
- **Jeppesen / Navigraph** charts are licensed per subscriber. They are never bundled, and a Stratos Premium entitlement is not a Jeppesen or Navigraph licence.
- **SkyVector, AirNav, OurAirports** remain optional outbound links from the airport page; they are not embedded and their terms are their own.

### Chart viewer and caching rules

- The catalogue request is answered by the bridge (`/charts?icao=`) or the hosted API (`/api/charts?icao=`). Both only ever read the FAA publication. A document request names a cycle and a PDF filename and nothing else: `^\d{4}$` for the cycle, `^[A-Z0-9]{1,12}\.PDF$` for the file. No arbitrary URL, header or credential is forwarded. The bridge refuses a document from a cycle other than the one it currently holds.
- Downloaded documents are cached in a separate IndexedDB database (`stratos_charts`), capped at 40 documents / 30 days. Clearing site data clears them.
- The FAA publication window from the metafile is shown with every chart. A document whose window has passed is labelled expired; if the window is missing it is labelled unverified. Stratos never calls a chart current without the publisher's dates.

## Stratos EFB

The electronic flight bag (`app/efb.html`) is a second surface over the same data, not a second data source. Nothing in it is invented, and each app states where its numbers came from.

- **Briefing** reads the SimBrief flight plan the tracker already stored (or the route the Flight Deck has loaded). Identity, procedures, runways, times, weights and fuel are labelled `OFP`; the route table is the plan's own navlog; and the published OFP PDF is the link SimBrief itself generated. A field the plan does not carry is shown as unavailable rather than filled in, and a plan with no navlog says so.
- **Charts** uses the FAA d-TPP catalogue described above, with the same provider registry, validity window, viewer, cache and Premium rule (ILS/LOC free, other categories gated). Airports outside the integrated coverage list publisher links only.
- **Weather** is the same NOAA Aviation Weather Center METAR/TAF text, decoded locally into wind, visibility, cloud, temperature and QNH, with observation time and age shown. Runway wind components are vector arithmetic on the runway heading. Where no verified free SIGMET feed is configured, the app says that instead of showing an advisory, and it links the official sources.
- **Performance** separates what can be computed from what must be published. Pressure altitude, ISA temperature and deviation, density altitude, and head/cross/tail wind are standard-atmosphere and vector calculations, computed for any type. V-speeds and field lengths are **not** computed: they exist only when a validated, aircraft-specific dataset is imported, are read by trilinear interpolation inside the dataset's own weight/pressure-altitude/temperature axes, and are never extrapolated beyond them. No manufacturer or third-party performance dataset is bundled, copied or scraped, and Stratos does not claim an approved dataset it does not hold; the app is labelled a simulator planning aid, not certified performance and not for real-world dispatch. Runway slope, contamination, bleed, anti-ice and obstacle corrections are applied only where the imported dataset itself publishes them.
- **Weight & Balance and Fuel** use the SimBrief weights and fuel figures when a plan is loaded (labelled `OFP`) or values the pilot enters (labelled as entered). Limits and centre-of-gravity arms are shown only when the aircraft's own data provides them; without arms and moments the app explains why it cannot give a CG instead of showing one.
- **Documents** presents the same community checklists and limitations as the tracker, with the same unverified label. No manufacturer FCOM/QRH or add-on EFB file is bundled.
- **Flight Planner** builds a plan against a chart of real navigation data, per the sections above: the departure rule, the route, published procedures only where the data publishes them, fuel that names its source, alternates that explain themselves, and weather that carries its observation time. Its globe offers four surfaces — **Outlines** (the bundled Natural Earth outlines, the default and the only one that needs no network), **Imagery** (NASA), **Relief** and **Elevation** (both from the same terrain tiles, shaded per surface so switching between them changes the picture) — with a camera reset back to the route, and the route, its points and the query radius are identical in both projections. **Reset plan** clears the departure, route, procedures, fuel and alternate, removes the copy of the route the Navigator and the Flight Deck read, and leaves the pilot's saved plans alone.
- **Live Flight** renders the existing bridge telemetry through the same map component as the phone, and **Logbook** reads the same local logbook; the EFB creates no second tracking system and no second store.
- Settings, the flight plan and checklist progress are kept in this browser/desktop app's own storage. No analytics or third-party request is added by the EFB.

## Relay and privacy

- The optional relay is part of this project. It stores SHA-256 token hashes and the latest telemetry snapshot; it does not store a flight history or user identity. It has no command channel to the simulator PC.
- No analytics, advertising SDK or third-party tracking is included. The logbook is local to the browser/desktop app; the relay is only used after the user explicitly pairs a phone.
